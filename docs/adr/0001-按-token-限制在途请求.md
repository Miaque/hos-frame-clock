# 按 Token 限制在途请求，超出的调用在库内排队

0.3.0 按配置顺序轮询分配 Token、不限制并发，并发数超过 Token 数时同一 Token 会被多个在途请求同时占用，调用方无法从"有几个 Token"推断"能发几个并发"。0.4.0 起每个 Token 同时最多服务 `PADDLEOCR_CONCURRENCY_PER_TOKEN` 个在途请求，超出的调用等待最先空闲的 Token，等待计入总超时；同时移除 `token` 参数，让并发上限完全由配置决定。排队而非快速失败，是因为调用方按帧批量调用时希望"最终都识别"而不是"自己再写一层限流"；不把限流交给服务端，是因为服务端限流表现为不可区分的 `OCRServiceError`，调用方无法据此做出正确的重试决策。
